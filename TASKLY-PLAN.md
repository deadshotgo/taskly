## 1. Що будуємо

Дві служби, кожна зі своєю базою, звʼязані подіями й одним синхронним викликом:

```
             HTTP/JSON                         gRPC
 клієнт ───────────────> taskly-api ─────────────────────────┐
                          │    │                               ▼
                          │    └─ outbox ──> Kafka ──> notifier ──> notifier-db
                          ▼                 (події)
                      taskly-db
```

| Служба | Відповідає за | Назовні |
|---|---|---|
| `taskly-api` | користувачі, воркспейси, проєкти, задачі, коментарі, авторизація | REST API (JSON) |
| `notifier` | сповіщення: «тобі призначили задачу», «задачу закрито» | gRPC API, читає події з Kafka |

**Чому саме так:**
- **Kafka** — асинхронно: `taskly-api` не чекає, поки сповіщення збережуться, і не падає, якщо `notifier` лежить.
- **gRPC** — синхронно: `GET /me/notifications` у `taskly-api` питає `notifier` через gRPC і віддає клієнту.
- **Своя база в кожної служби** — служби не лізуть у таблиці одна одної. Це головне правило мікросервісів.
- **Outbox** — подія пишеться в ту саму транзакцію, що й зміна задачі, тож не буває «задачу змінили, а подія загубилась».

Домен `taskly-api` — як у `CAPSTONE.md`, розділ 1.

## 2. Стек

| Шар | Вибір | Примітка |
|---|---|---|
| HTTP | stdlib `net/http`, `http.ServeMux` (Go 1.22+ патерни) | без фреймворків |
| БД | PostgreSQL, `pgx/v5` (pool) | SQL руками або `sqlc`, без ORM |
| Міграції | `golang-migrate` або `goose` | `.sql` файли в репо |
| Логи | `log/slog`, JSON | `request_id` у кожному рядку |
| Конфіг | змінні оточення → `Config` + валідація | `.env.example` без секретів |
| Kafka | клієнт `franz-go` (`twmb/franz-go`); запасний варіант `segmentio/kafka-go` | брокер у Docker у режимі KRaft |
| gRPC | `google.golang.org/grpc` + protobuf | генерація через `buf` |
| Тести | `testing`, `httptest`, `testcontainers-go` | `-race` завжди |
| Метрики / трейси | Prometheus, OpenTelemetry | трейс проходить HTTP → Kafka → gRPC |
| Запуск | Docker multi-stage, `docker compose` | усе піднімається однією командою |
| CI | GitHub Actions | `gofmt`, `go vet`, `staticcheck`, тести з `-race`, збірка |

Конкретні версії бібліотек і точні API перевіряємо в документації на момент етапу, не з памʼяті.

## 3. Структура репозиторію

Окремий git-репозиторій (твій новий репо на GitHub), відкритий у GoLand окремим проєктом.
Два Go-модулі звʼязані `go.work`. Уроки курсу лишаються в `~/GolandProjects/courses/lessons/`.

```
taskly/
├── go.work                      звʼязує два модулі для локальної розробки
├── proto/                       .proto-файли — контракт gRPC, спільний для обох служб
│   └── notifier/v1/notifier.proto
├── buf.yaml, buf.gen.yaml       генерація Go-коду з proto
├── services/
│   ├── taskly-api/
│   │   ├── go.mod
│   │   ├── cmd/api/main.go      збирає залежності, запускає сервер, чекає сигналу зупинки
│   │   ├── internal/
│   │   │   ├── config/          Config з env + валідація
│   │   │   ├── domain/          чисті типи й правила: Task, Status, переходи, помилки. Без http/sql
│   │   │   ├── service/         бізнес-логіка; тут оголошені інтерфейси репозиторіїв
│   │   │   ├── storage/postgres/ репозиторії, транзакції, outbox-таблиця
│   │   │   ├── httpapi/         роутер, хендлери, DTO, middleware, writeJSON/writeError
│   │   │   ├── events/          outbox relay → Kafka, схеми подій
│   │   │   ├── notifierclient/  gRPC-клієнт до notifier з дедлайнами
│   │   │   └── auth/            Argon2id, токени
│   │   └── migrations/
│   └── notifier/
│       ├── go.mod
│       ├── cmd/notifier/main.go запускає Kafka-консюмер і gRPC-сервер разом
│       ├── internal/
│       │   ├── config/, domain/, service/, storage/postgres/
│       │   ├── consumer/        читання подій, ідемпотентність, повтори, DLQ
│       │   └── grpcapi/         реалізація gRPC-сервісу
│       └── migrations/
├── deploy/
│   └── docker-compose.yml       postgres (дві бази), kafka, обидві служби, prometheus
├── Makefile                     run, test, lint, migrate, proto, up/down
└── README.md                    як запустити, схема, API
```

**Напрямок залежностей** усередині служби:

```
httpapi / grpcapi / consumer ──> service ──> storage, events, notifierclient
          └───────────────────────┴──────────┴──────────────> domain
```

`domain` не імпортує нічого свого. `service` не знає ні про HTTP, ні про Kafka, ні про gRPC.

## 4. Правила для всього коду

Це перевірятиму на кожному ревʼю.

1. **`context.Context` — перший параметр** кожної функції, що ходить у мережу чи базу.
2. **Таймаут на кожному зовнішньому виклику:** HTTP-сервер, запит до БД, gRPC (дедлайн), Kafka.
3. **Помилки:** обгортання `fmt.Errorf("контекст: %w", err)`, sentinel-помилки в `domain`, маппінг на HTTP-статус чи gRPC-код **в одному місці**. Логує лише верхній шар.
4. **Логи:** лише `slog`, JSON, з `request_id` (і `trace_id`, коли додамо трейсинг). Жодних `fmt.Println` у сервісах. Паролі й токени в лог не потрапляють.
5. **Конфіг лише з env**, перевіряється на старті. Немає обовʼязкової змінної → служба не стартує з зрозумілою помилкою.
6. **Інтерфейси оголошує споживач**, маленькі, по 1–4 методи. Залежності передаються в конструктор `New...`, без глобальних змінних.
7. **Коректна зупинка:** на SIGTERM сервер дочитує запити, консюмер закінчує поточне повідомлення, пули закриваються.
8. **Події ідемпотентні:** у кожної є `event_id`; консюмер, отримавши ту саму подію вдруге, нічого не дублює.
9. **Тести:** table-driven для `domain`, `httptest` для хендлерів, `testcontainers` для репозиторіїв і Kafka. `go test -race ./...` зелений.
10. **Відповіді API** в одному форматі; порожній список — `[]`, а не `null`.

## 5. Етапи

Кожен етап — це те, що можна показати й запустити. Уроки в колонці «Читати» — теорія перед етапом.
Задачі з уроків не робимо, замість них — сам етап.

### S0 — Середовище
**Читати:** урок 13 (пакети й модулі).
- **Docker-first:** усе, що запускається (бази, Kafka, обидві служби), живе в `docker compose` з першого дня.
  Локально лишається лише Go-тулчейн для GoLand, `gofmt`/`vet`/тестів.
- Корінь цього репо з `go.work`, двома модулями й мінімальними `main` (пишуть один slog-рядок і чекають сигналу).
- Multi-stage `Dockerfile` для кожної служби: `dev` (Go + `air`, код через bind mount) і `prod` (distroless, ~10 МБ), `.dockerignore`.
- `deploy/docker-compose.yml`: PostgreSQL з healthcheck і volume, дві служби з `target: dev`; live reload
  через `air` у контейнері. Makefile: `make up`, `make down`, `make logs`, `make check`.
- **Готово, коли:** `make up` піднімає базу й обидві служби, `docker compose ps` показує їх живими,
  зміна в `main.go` перезбирає контейнер, `go build ./...` локально проходить.

### S1 — Скелет `taskly-api`
**Читати:** 21 (`net/http`), 23 (`slog`), 26 (конфіг, таймаути, graceful shutdown).
- `Config` з env, `slog` у JSON, HTTP-сервер з таймаутами, `/healthz`, коректна зупинка на Ctrl+C.
- Логер з вибором формату через `LOG_FORMAT=pretty|json`: кольоровий (`lmittmann/tint`, API звірити з докою) для розробки, JSON для продакшну. Перевірити кольори в `docker compose logs`.
- **Готово, коли:** сервер стартує, пише JSON-логи, `/healthz` відповідає `200`, Ctrl+C зупиняє без обірваних запитів.

### S2 — Задачі в PostgreSQL + REST
**Читати:** 10 (розділи 1–6), 11 (1–3, 6), 15 (JSON), 22 (JSON API), 24 (шари), 25 (PostgreSQL).
- Перша міграція: таблиця задач. Пул `pgx` з таймаутами. `/readyz` перевіряє базу.
- `domain`: твій `Task` з уроку 10.1, статуси, переходи (задача 10.3), помилки.
- Репозиторій → сервіс → хендлери: `POST /tasks`, `GET /tasks/{id}`, `GET /tasks`, `PATCH /tasks/{id}` (часткове оновлення, урок 09.5).
- Єдиний формат помилок, маппінг `ErrNotFound → 404`, `ErrValidation → 400`, `ErrBadTransition → 409`.
- Middleware: `request_id`, лог запиту, recover.
- **Готово, коли:** задачі створюються й змінюються через `curl`, після перезапуску дані на місці, кожен лог має `request_id`.

### S3 — Тести
**Читати:** 14 (тести), 29 (тестування по-дорослому).
- Table-driven тести переходів статусів і валідації назви.
- Тести хендлерів через `httptest` з фейковим сервісом.
- Інтеграційні тести репозиторію на справжньому PostgreSQL через `testcontainers`.
- **Готово, коли:** `go test -race ./...` зелений, а зламаний перехід статусу ловиться тестом.

### S4 — Конкурентність у сервері
**Читати:** 16–20 (горутини, канали, `select`, мʼютекси, `context`).
- Таймаути запитів до БД через `context`; скасування, коли клієнт пішов.
- Фоновий воркер: раз на хвилину шукає задачі з простроченим дедлайном (`time.Ticker` + `select` + зупинка через `context`).
- Запуск сервера й воркера разом, зупинка обох коректно (`errgroup`).
- **Готово, коли:** `-race` чистий, Ctrl+C зупиняє і сервер, і воркер, а повільний запит обривається по таймауту.

### S5 — Аутентифікація
**Читати:** 27.
- Реєстрація, логін, Argon2id, access-токен (JWT) + refresh-токен з ротацією, middleware авторизації.
- **Готово, коли:** без токена `401`, з простроченим `401`, повторне використання refresh-токена відкликає всю сесію.

### S6 — Воркспейси, проєкти, ролі
**Читати:** 28.
- Сутності й матриця прав з `CAPSTONE.md`, розділи 1 і 4.4. Перевірка доступу на рівні ресурсу.
- **Готово, коли:** чужий користувач отримує `404` на чужу задачу, `member` не може видалити проєкт.

### S7 — Події: outbox + Kafka
**Читати:** 33 (надійність, ідемпотентність), 35 (фонова робота); **новий урок 37 — Kafka** (згенерую перед етапом).
- Kafka в `docker compose`. Топік `task-events`.
- Таблиця `outbox`: подія пишеться **в тій самій транзакції**, що й зміна задачі.
- Relay-воркер читає outbox і публікує в Kafka, позначає відправлене. Повтори з backoff.
- Події: `task.created`, `task.assigned`, `task.status_changed`, кожна з `event_id`, часом і версією схеми.
- **Готово, коли:** зупинив Kafka → змінив задачу → підняв Kafka → подія таки дійшла.

### S8 — Служба `notifier`: Kafka-консюмер + gRPC
**Читати:** **новий урок 38 — gRPC і protobuf** (згенерую перед етапом).
- Окремий модуль, своя база, свої міграції.
- Консюмер з consumer group: зберігає сповіщення, ідемпотентно за `event_id`, погані повідомлення — у DLQ-топік.
- `proto/notifier/v1`: `ListNotifications`, `MarkRead`. gRPC-сервер з перехоплювачами (interceptors) для логів і recover.
- У `taskly-api`: gRPC-клієнт з дедлайном і `GET /me/notifications`. Якщо `notifier` недоступний — зрозуміла помилка `503`, а не зависання.
- **Готово, коли:** призначив задачу → за секунду сповіщення видно через `GET /me/notifications`; вимкнув `notifier` → `taskly-api` працює далі.

### S9 — Спостережуваність
**Читати:** 30 (observability), 31 (профілювання — вибірково).
- Метрики Prometheus: кількість запитів, помилки, тривалість; лаг консюмера.
- OpenTelemetry: один `trace_id` від HTTP-запиту через Kafka до `notifier` і назад через gRPC.
- **Готово, коли:** за `trace_id` з логу видно весь шлях однієї дії через обидві служби.

### S10 — Делівері
**Читати:** 32 (безпека), 36 (архітектура й делівері).
- Довести Dockerfile до продакшн-рівня (non-root, distroless/scratch, мінімальний розмір), повний `docker compose up` з Kafka й notifier.
- GitHub Actions: lint, vet, тести з `-race`, збірка образів.
- README: схема, як запустити, приклади запитів.
- **Готово, коли:** чиста машина → `git clone` → `make up` → усе працює.
